# 完整 binlog 压缩主档（源代码候选，默认不启用）

目标是所有 OSS 存储合计尽量小，不为 5 TB 更改查询语义或丢失历史。原生产 62 天 ClickHouse 表、关键词索引、历史定位符与 TTL 均不变。发布候选 1.42.3 基于 1.42.2（9f2beb0），写开关默认关闭。镜像发布以云端 CI 结果为准，线上切换以运行实例的镜像摘要及验收结果为准。

- 新读取端同时支持旧裸对象及 v2；写入开关为 `RDS_BINLOG_WRITE_FRAMED_ZSTD=1`。处理新文件时先把原文按 8 MiB 独立帧压缩到本地临时文件，每帧当场解压比对、整份检查原文 SHA-256/CRC64，再走原有禁止覆盖的 OSS 上传、HEAD 及重试路径。不再把裸 `.binlog` 上传一遍。分帧开销、实际压缩比和吞吐须以 8 MiB 格式而非旧作业测量。预留最坏情况下接近一个原文件大小的本地临时空间。
- 新前缀 `binlog-recovery/v2/` 含版本化压缩对象、轻量索引和恢复清单；帧目录、原文件身份及哈希也随清单保存在 OSS。清单成功前不登记归档；回滚/暂停不能手动清除已有的 v1/v2 对象。独立灾备还需要采集登记/缺口、模式注册表、应用配置和可用解析器，不把此清单称为整机备份。
- 滚动顺序：先给全部消费者部署可读 v2 的版本但保持写开关关闭；独立备份目标/权限与本前缀 62 天生命周期和边界文件恢复窗口须由 DBA 核实后再启写。现有 v1 的 7 天/标签 2 天规则和父路径 60 天规则都不能直接用于此新前缀。若按上传时间的 62 天不能覆盖按事件时间的窗口，则延长边界保护。先隔离跑单文件原始解析输出对比，再验证跨日查询、关键词、分页、旧链接、聚合、缺口和重建耗时。只在 v2 确认覆盖后退出 v1 旁路压缩；未覆盖的旧数据先备份，不当作重复删除。
- 关写开关只影响之后的新文件；仍有 v2 数据时不能回退到只读 v1 的旧二进制。恢复必须从 manifest 验证所有帧、原文 SHA-256/CRC64 及索引，之后用同版本 parser 在隔离实例重放。
- 离线恢复：在项目根目录以 `python -m app.restore_frames MANIFEST ZSTD LITE_INDEX NEW_DIRECTORY` 执行。前三个参数是从同一批备份取回的本地文件路径（manifest 保留对象原文件名），最后一个是不存在的输出目录；只接受出现 `READY` 的结果。不会覆盖已有输出，也不会写回 OSS。得到原始 `source.binlog`、轻索引及 manifest 后，才进行隔离入库和页面回放。
- `tools/compare_lossless.py` 是隔离实验工具，不更改线上表。输入最多 16 MiB/16384 行的 JSONEachRow（`before_json`/`after_json` 或 `row_query`），验证字节可逆，输出 Zstd3 压缩后的对照字节数，含模板字典、参数或差量边界。不输出正文。样本节省不能作为整表收益；只有连索引、辅助列、独立灾备实际总字节更少且恢复/性能无退化才考虑切换。
