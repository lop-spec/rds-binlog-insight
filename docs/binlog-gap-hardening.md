# Binlog 采集不留缺口（1.35.0–1.35.2）

RDS 只把已轮转、已上传的 binlog 保留 `LogBackupRetentionPeriod` 天（默认 7 天，每个任务开头读备份策略）。超过这个期限还没采到的文件，源端会删除，之后无法补采。1.35.0 的目标是：凡是采集端能避免的缺失，都不再发生；避免不了的缺失（源端已删、源端从未上传），要被检测出来并报告，不能被当成"已覆盖"。

## 采集链路的保证

| 环节 | 以前 | 现在 |
|---|---|---|
| 任务卡死 | 一个任务无进展 10 小时，健康接口只记 `stalled` | 看门狗：30 分钟无进展（列表页、下载字节、扫描、上传分片、文件状态都算进展）先请求任务在文件边界停下，调度器立即开新任务；10 分钟后仍未停下，写全部线程栈到 `logs/sync-stall-*.txt` 并退出进程，由 supervisor 拉起。调度循环 2 小时不跳动同样处理 |
| 单个文件失败 | 整个任务失败，正在下载的文件全部中断；下个任务又先处理这个文件（头部阻塞，曾连续 6 天） | 文件级隔离：失败的文件按 1、2、4…30 分钟退避重试，其他文件继续；连续 8 个文件失败才判定为公共故障（网络、凭据、OSS）让任务失败。权限类错误仍立即失败 |
| 元数据库写锁 | `database is locked`（5 秒）直接让任务失败 | 采集路径的写入遇锁最长等 60 秒（`RDS_BINLOG_METADATA_BUSY_RETRY_SECONDS`） |
| 下载 | 一次网络抖动/5xx/校验失败即失败 | 文件内续传重试 2 次（5 秒、20 秒）；下载前检查磁盘余量（文件大小 + 20 GiB），不足时等待而不是写到一半失败 |
| 超大文件 | 超过 4 GiB 准入预算的文件单独准入，期间其他文件全部等待 | 超大文件走独立通道，普通文件照常准入 |
| 轻量索引扫描 | 扫描超时（固定 180 秒）、目录超限或事件布局不认识，原文件永远归档不了 | 原始字节优先：扫描失败时以整文件保守目录完成归档（查询把它当候选文件），日志 `RAW_INDEX_OPAQUE`；超时按文件大小放宽（每 GiB 加 60 秒）。不是 MySQL binlog 的文件仍报错 |
| 原档已上传但状态未完成 | 重启后重新下载；源端已删时被标为"不可用" | 先查原档目录，校验 OSS 后直接完成 |
| "实例未找到" | 刷新链接时按完整标识查不到就永久标为不可用，之后再被列出也不重试 | 未到源端保留期的只记失败、退避重试；再次被列出的不可用文件自动恢复采集；同名同节点但大小/时间变化的按新标识采集（旧行记 `superseded`） |
| 主节点切换 | 只认当前主节点：前主未采完的文件永久丢弃；新主切换前作为备库写的文件全部重采（同一时间段行数据重复） | 主机延续规则（`HostPlan`）：已登记文件的主机就是时间线；新主的文件被其他主机已登记文件完全覆盖的不采，前主在新主接手前的文件继续采；纯备库的文件永不采。任务内每 5 分钟重读主节点；读主节点失败时沿用上次主节点 |
| 发现（列文件） | 一次 60 天偏移分页扫描（6 个节点的文件，约 40 分钟），期间文件上传/过期会使分页漂移；实时窗口只看 1 小时；任务开始后才上传的晚到文件要等下个任务 | 只扫源端保留期 + 1 天，按 6 小时切片分页，单片页数漂移时重扫该片；每 10 分钟补列 1–6 小时前的晚到窗口；每小时重复一轮保留窗口扫描；按节点检查 `mysql-bin` 序号断档，断档时间段定向补查 |
| 云 API | 一次限流/超时让任务失败 | 限流、5xx、网络错误重试 2 次（新签名）；实时列表失败 10 分钟内只记日志 |
| OSS 生命周期规则 | 读写规则失败让每个任务在发现前失败 | 降为告警（1.35.1）；桶访问仍必须正常 |
| 上传中的文件 | 上传中即登记，完成后大小/时间若变化留下永远“采集中”的行 | 完成后再登记（1.35.1） |
| 积压接近源端保留期 | 冷热交替，最老文件只得一半通道 | 距源端删除不足 2 天的文件最先处理（最老优先），准入放宽到 12 个文件 / 6 GiB，并跳过轻量扫描先保原始字节 |

## 入库（按表存储）的保证

- 失败的文件不再"3 次后放弃到进程重启"：按 30 秒起翻倍、最长 30 分钟退避，任何通道都会重试；失败 5 次以上的文件写进状态文件 `stuckFiles` 并在健康接口报出。
- 缓冲表放宽 parts 上限（`parts_to_delay_insert`/`parts_to_throw_insert`），写入块改为 65 536 行或 32 MB：一个 23 GB 的单事务 binlog 曾产生约 2 800 个 part，接近拒写上限 3 000。
- RowBinary 加载失败时先报 OSS 读取或解析器的真实原因，不再只报 ClickHouse 的 `Cannot read all data`。

## 缺口报告

查询结果与 `/api/index-coverage` 按时间并集计算覆盖，每段缺口都有原因：

| 原因 | 含义 |
|---|---|
| `source_missing` 源 Binlog 缺失 | 源端已删或从未提供（含时间断档超过源端保留期） |
| `source_unlisted` 源未列出 | 这段时间没有任何已登记文件，仍在源端保留期内，采集端会定向补查 |
| `collecting` 采集中 | 文件已发现、尚未采集完 |
| `pending` 未入库 | 已采集，尚未进入按表存储 |
| `not_collected_yet` 尚未采集 | 最新文件之后（源端文件尚未轮转或上传） |
| `no_data` 无数据 | 最早文件之前 |

以前两个已入库文件之间的时间断档（未登记的文件）会被当成已覆盖；单事务大文件（开始等于结束时间）未入库时也不报缺口。现在都会报出。另一主机已入库的同时间段副本视为已覆盖。

覆盖计算每个缺失文件只查与它相交的已覆盖时间段（二分查找），其他主机的覆盖每台主机只算一次（1.35.2）；1.35.0–1.35.1 的逐段相减随缺失文件数平方增长，生产实例 60 天覆盖查询要约 11 秒。

## 健康与告警

`GET /api/sync/health` 每个实例增加 `binlog`：

- `lagSeconds`：最老未采集文件的滞后；`expiresInSeconds`：距源端删除它还有多久。
- 状态：`lost`（近 24 小时有保留期内的源文件变为不可用）、`expiry_risk`（不足 2 天就会被源端删除）、`stuck`（失败 5 次以上）、`behind`（滞后超过 30 分钟）。任一出现即 HTTP 503。

另有 `rows`：按表存储落后采集超过 1 小时、写入进程 15 分钟没有更新状态、或有反复失败文件时为不正常。过期且未采到的未完成文件每小时标为 `unavailable`（`SOURCE_EXPIRED`），不再长期算作"待采集"。

## 仍然做不到的

- 源端已删除的历史文件无法补回。
- 低写入实例的 binlog 要等轮转后才会上传，尾部几个小时"尚未采集"属源端行为；提前轮转需要 `FLUSH BINARY LOGS` 权限，本工具不做写操作。
- 主节点的某个文件在源端损坏或从未上传时，不会自动改用备库同时间段的文件补位（需要按 GTID 去重，未实现）；这类缺口会以 `source_missing`/`source_unlisted` 报出。
- 按表存储的吞吐约为业务高峰的 2 倍；更大的持续洪峰下入库会落后（原档在 OSS 保留 60 天，不丢数据），提高吞吐需要更多 CPU，未做。

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `RDS_BINLOG_SOURCE_RETENTION_DAYS` | 7 | 读不到备份策略时的源端保留天数 |
| `RDS_BINLOG_SYNC_STALL_SECONDS` | 1800 | 无进展多久请求任务停下 |
| `RDS_BINLOG_SYNC_EXIT_GRACE_SECONDS` | 600 | 请求后多久仍未停下就重启进程 |
| `RDS_BINLOG_SCHEDULER_STALL_SECONDS` | 7200 | 调度循环多久不跳动就重启进程 |
| `RDS_BINLOG_METADATA_BUSY_RETRY_SECONDS` | 60 | 元数据写入遇锁的最长等待 |
| `RDS_BINLOG_DOWNLOAD_DISK_RESERVE_GIB` | 20 | 下载准入要保留的磁盘余量 |
